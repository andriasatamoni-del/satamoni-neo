# النسخ الاحتياطي والاسترجاع

## الطبقات

1. **النسخ الاحتياطي بتاع مزوّد قاعدة البيانات نفسه (الأساس)** - على Render، الخطط المدفوعة لـPostgres
   فيها نسخ تلقائي يومي + Point-In-Time Recovery (استرجاع لأي لحظة، مش بس آخر نسخة يومية). ده لازم يتفعّل
   قبل التشغيل الفعلي. **خطة Free ملهاش نسخ احتياطي خالص وقاعدتها بتنتهي بعد فترة** - متتشغلش عليها بيانات حقيقية.
2. **نسخة يومية مستقلة عن Render (الطبقة دي)** - `pg_dump` يومي عن طريق GitHub Actions، وتمرين استرجاع
   حقيقي على كل نسخة. مفيدة لو حساب Render نفسه حصله حاجة، أو لنقل الاستضافة.

## النسخ اليومي التلقائي (GitHub Actions) — محدَّث في Phase 3.1 (BL-13)

الملف: `.github/workflows/db-backup.yml`، كل يوم 01:07 UTC (بعد نص الليل بتوقيت القاهرة)، مربوط بـEnvironment
اسمه `production-backup`. **السبب الأصلي لفشله**: `defaults.run.working-directory: backend` كان بيتطبق على أول خطوة
(قبل `checkout`) فالـjob كان بيموت قبل أي نسخة. اتصلّح، وبقى:

1. **تحقق من الإعداد**: لو `DATABASE_URL` أو `BACKUP_ENCRYPTION_KEY` (≥ 32 حرف) ناقصين الـjob **بيفشل بصوت عالي** (مفيش
   skip صامت). القيم عمرها ما بتتطبع.
2. `pg_dump -Fc` + تحقق: حجم أدنى، `pg_restore --list` بيقرا الفهرس كله (بيكشف النسخة المقطوعة/التالفة)، وملف `.sha256`.
3. **تمرين استرجاع** على سيرفر Postgres مؤقت داخل الـjob (مش الإنتاج)، بيتأكد من الجداول/البيانات/اتزان القيود،
   وبيقارن النسخة المسترجعة بالأصل (عدّادات، أرصدة المخزون، مجاميع القيود، أدوار المستخدمين، عدد الـmigrations).
4. **تشفير** الملف (`gpg --symmetric AES256`) وإثبات إن المفتاح بيفك التشفير، وبعدين مسح النسخة غير المشفرة. الـartifact
   (30 يوم) فيه `*.dump.gpg` بس — حتى لو الريبو public مفيش حد يقدر يقراه من غير `BACKUP_ENCRYPTION_KEY`.
5. **تخزين مستقل (اختياري لكن مطلوب للتشغيل الحقيقي)**: لو `BACKUP_S3_BUCKET` وباقي أسرار S3 متضافة، النسخة المشفرة بتتنسخ
   لتخزين S3-compatible مستقل وبتتطبق سياسة الاحتفاظ (يومي/شهري/سنوي) هناك. **لو مش متضاف الـworkflow بيطلّع تحذير: artifacts
   لوحدها (≤ 90 يوم) مش استراتيجية نسخ احتياطي طويلة المدى.**

فك التشفير: `gpg --decrypt satamoni-neo-YYYYMMDD-HHMMSS.dump.gpg > file.dump` (هيسألك عن المفتاح) ثم `pg_restore`.
**احتفظ بـ`BACKUP_ENCRYPTION_KEY` في مدير كلمات سر — من غيره النسخ مش قابلة للاسترجاع.**

### سياسة الاحتفاظ (قابلة للاختبار تشغيليًا)

* كل نسخة في آخر `BACKUP_DAILY_RETENTION_DAYS` (30) يوم بتتحفظ.
* بعدها أقدم نسخة في كل شهر لحد `BACKUP_MONTHLY_RETENTION_MONTHS` (12) شهر.
* بعدها أقدم نسخة في كل سنة للأبد.
* ملفات بأسماء مش مطابقة للنمط عمرها ما بتتمسح.

اختبرها من غير ما تمسح حاجة: `npx ts-node scripts/backup/retention-plan.ts --dir ./backups --now 2026-10-02T00:00:00Z`
(بيطبع KEEP/DELETE/IGNORE). نفس المنطق بيتطبق على قايمة أسماء من S3 (`--names-file ... --suffix .gpg --print-delete`).
مغطّاة باختبارات `test/unit/scripts/backup-retention-plan.spec.ts` (محاكاة 3 سنين نسخ يومية).

> لم يتم تنفيذ أي نسخة إنتاج فعلية بواسطة الأدوات؛ **مفيش ادّعاء إن نسخ الإنتاج موجودة** لحد ما تشغّل الـworkflow
> بعد ضبط الـsecrets ويعدّي تمرين الاسترجاع بنجاح (راجع `docs/SECURITY_HARDENING.md` §4).

## تشغيل يدوي

```bash
cd backend
# نسخة احتياطية + سياسة الاحتفاظ (30 يوم يومي / 12 شهر شهري / سنوي للأبد)
DATABASE_URL=postgres://... PGSSL=true BACKUP_DIR=/path/to/backups npm run backup

# تمرين استرجاع على أحدث نسخة في BACKUP_DIR (أو --backup=/path/file.dump)
RESTORE_DRILL_DATABASE_URL=postgres://user:pass@localhost:5432/postgres BACKUP_DIR=/path/to/backups npm run restore-drill
```

| المتغير | الافتراضي | الوصف |
|---|---|---|
| `BACKUP_DIR` | `./backups` | مجلد ملفات النسخ (متجاهَل في git) |
| `BACKUP_DAILY_RETENTION_DAYS` | `30` | كل النسخ في النافذة دي بتتحفظ |
| `BACKUP_MONTHLY_RETENTION_MONTHS` | `12` | بعدها أقدم نسخة في كل شهر بس، وبعدها أقدم نسخة في كل سنة للأبد |
| `RESTORE_DRILL_DATABASE_URL` | `DATABASE_URL` | سيرفر Postgres تقدر تعمل عليه قاعدة مؤقتة - **مش الإنتاج** |

الباسورد بيتبعت لـ`pg_dump`/`pg_restore` كمتغير بيئة (`PGPASSWORD`)، مش في سطر الأوامر، عشان ميظهرش في `ps`.

## تمرين الاسترجاع بيتحقق من إيه

1. إنشاء قاعدة مؤقتة نضيفة باسم فريد.
2. `pg_restore` للنسخة فيها.
3. الجداول الأساسية من كل context موجودة.
4. فيه بيانات حقيقية (فرع واحد على الأقل - الـmigrations نفسها مبتزرعش فروع).
5. كل القيود المحاسبية المرحّلة/المعكوسة متزنة (مدين = دائن).
6. تشغيل `migrateToLatest` على النسخة المسترجعة - بيثبت إن نسخة قديمة (قبل آخر deploy) تقدر تتسترجع
   وتتحدّث للكود الحالي. ده السيناريو الحقيقي وقت أزمة.
7. مسح القاعدة المؤقتة (إلا لو `--keep`).

`exit code` = `0` لو كل الفحوصات نجحت، `1` لو أي حاجة فشلت.

## الاسترجاع الفعلي وقت أزمة

1. أوقف الباك إند (Render → Suspend) عشان محدش يكتب بيانات جديدة أثناء الاسترجاع.
2. **الخيار الأول دايمًا**: استرجاع من لوحة Render (PITR) للحظة قبل المشكلة.
3. لو مش متاح: اعمل قاعدة جديدة، و`pg_restore --no-owner --no-privileges -d <new-db> <file.dump>`،
   وبعدين غيّر `DATABASE_URL` في الباك إند للقاعدة الجديدة. أول تشغيل هيطبّق أي migration ناقصة تلقائيًا.
4. شغّل الباك إند، واعمل اختبار دخان (تسجيل دخول + طلب + قيد محاسبي).
